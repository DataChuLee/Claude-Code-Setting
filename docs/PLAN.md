# 목표
나는 AI Engineer 취업을 준비 중이고, AI-Native Development 하네스 환경을 직접 구축하며 배우려고 한다.
"이슈 → 구현 → 검증 게이트 → PR → 리뷰/머지 → 배포 → 관측 → 개선" 흐름을 Phase별로 만든다.
결과물뿐 아니라 내가 이해하는 것이 중요하다.

# 진행 규칙
1. 매 세션에서 지정한 Phase 하나만 진행한다. 먼저 plan 모드로 계획을 세우고, 불명확한 점은 질문한다.
2. Phase가 끝나면 (a) 무엇을 만들었는지, (b) 왜 그렇게 설계했는지, (c) 어떻게 검증했는지 설명하고,
   내가 확인하기 전에는 다음 Phase로 넘어가지 않는다.
3. 도구·설정 문법(settings.json, hooks, subagents, skills, GitHub Actions)은 기억에 의존하지 말고
   현재 버전의 공식 문서를 확인해서 작성한다.
4. 설계 결정과 이유, 겪은 실패와 해결을 docs/HARNESS.md에 누적 기록한다.
5. 지침 파일은 CLAUDE.md로 통일한다. 짧은 "지도"로 쓰고 길게 쓰지 않는다.

# 절대 하지 말 것
- 시크릿·토큰을 파일에 쓰거나 출력하는 것
- GitHub 브랜치 보호 규칙·저장소 설정을 직접 변경하는 것 (설정 방법만 안내, 내가 직접 한다)
- API 키를 다루는 것 (내가 GitHub Secrets에 직접 등록한다)
- 내 승인 없이 다음 Phase로 넘어가는 것
- 자동 머지 (머지는 항상 사람이 승인)

# Phase 1. 하네스 기본층
- CLAUDE.md: 프로젝트 규칙, 테스트·린트 명령, 금지 사항
- settings.json 권한(allow/deny)으로 위험 명령 차단
- 훅(PreToolUse/PostToolUse)으로 위험 동작 강제 차단
- "절대 하지 말 것" 항목(시크릿 접근, force push, main 직접 push 등)을 deny 규칙과 훅으로 구현하고,
  실제로 시도해서 차단되는지 테스트한 결과를 보여줄 것

# Phase 2. 검증 게이트
- 변경 후 테스트·린트·타입체크 자동 실행, 실패 결과가 에이전트에게 돌아가게 구성
- 구현과 분리된 리뷰 서브에이전트(.claude/agents/)가 변경을 검토
- 재시도 최대 2회. 말이 아니라 카운터 파일이나 훅으로 강제하는 방식을 먼저 설계해서 나에게 보여줄 것.
  초과하면 멈추고 사람에게 에스컬레이션
- 끝에서 게이트가 실제로 작동하는지 일부러 실패 상황(깨진 테스트, 위험 명령)을 만들어 검증하고 기록

# Phase 3. PR 자동화 (/ship 스킬)
- 브랜치 agent/<이슈번호>-<요약> 생성 → 커밋 → push → draft PR 생성
- main 직접 push 금지
- PR 본문 템플릿: 변경 이유(이슈 링크), 핵심 변경, 실행한 테스트와 결과,
  확인하지 못한 부분, 사람이 봐야 할 위험 지점, 리뷰 에이전트 지적과 반영 여부

# Phase 4. 루프 (Phase 1~3이 안정된 뒤에만)
- GitHub Actions로 특정 라벨이 붙은 이슈를 받아 Phase 2~3 자동 실행
- 트리거는 "저장소 소유자가 지정한 라벨이 붙은 이슈"로 제한. 이슈 본문은 신뢰하지 않는 입력으로 취급
- 최소 권한 토큰, 재시도 상한, PR 크기 제한
- 비용 상한을 설정하는 방법 안내

# Phase 5. 관측과 개선
- 실패 패턴을 LEARNING.md에 기록하고, 반복되는 실패를 규칙·훅·테스트로 환류하는 절차 작성
